# Deductrium 2.0 项目与创造模式说明

本文是 Deductrium 2.0 的项目总览和创造模式玩法笔记。重点是回答两个问题：项目由哪些部分组成，以及玩家在创造模式中如何使用这些部分进行形式化数学探索。

生存模式的地图、移动、奖励、推理素、闸门和成就经济不在本文范围内。代码中仍保留这些模块，但创造模式不会加载几何层，也不会保存生存模式的资源与解锁进度。

## 一、项目是什么

Deductrium 不是传统的关卡制解谜游戏，而是一个运行在浏览器中的数学推理沙盒。玩家通过可视化列表和命令栏：

- 创建假设、断言和推理步骤；
- 使用规则推导新的命题；
- 把一段已经完成的推理保存成新规则，继续组合和复用；
- 用元规则自动生成条件、量词和等价替换相关的推理；
- 在类型层输入 HoTT（同伦类型论）表达式，让内核检查其类型并归一化；
- 把证明过程组织成多个推理表、文件夹和定理表。

项目的核心体验是“写出形式化对象，然后让检查器确认它是否成立”。系统不会根据自然语言猜测证明，所有结果都必须通过解析器、规则匹配、断言求解器或类型检查器。

## 二、运行方式与整体架构

### 入口

- `index.html` 是主页面。
- `?creative` 进入创造模式；没有该查询参数时默认是生存模式。
- `lib/lz-string.min.js` 用于压缩浏览器本地存档。
- `js/` 是 `src/` 的 TypeScript 编译输出，平时应编辑 `src/`，不要直接修改 `js/`。
- `tsconfig.json` 将 `src/` 编译到 `js/`，目标为 ES2022，并生成 source map。

页面脚本加载几何层脚本和游戏总入口 `js/game.js`，再由 `Game` 根据模式初始化各层。语言由浏览器语言或 `localStorage` 中的 `lang`（`zh`/`en`）决定。

### 四个界面层

页面导航预留四层：

| 层 | 主要作用 | 创造模式 |
| --- | --- | --- |
| G-layer 几何层 | 双曲/几何世界、地图移动和生存玩法 | 不显示 |
| D-layer 推理层 | Hilbert 风格的一阶逻辑推理 | 显示 |
| T-layer 类型层 | HoTT 类型检查、定义和归约 | 显示 |
| P-layer 进度层 | 存档、槽位、统计、成就、知识库 | 显示 |

`src/game.ts` 是总装配入口：它创建 `HSLayer`、`TTLayer`、`HyLayer` 和 `ProgressLayer`，负责层切换、自动保存、模式判断和初始化规则。创造模式只把推理层和类型层作为可玩的数学系统；进度层主要承担存档与查看功能。

### 代码模块

- `src/hs/`：Hilbert 推理层。
  - `core/ast.ts`：抽象语法树 AST。
  - `core/parser.ts`：wff、rule、cmd 的解析器。
  - `core/core.ts`：规则注册、命题生成、规则应用、作用域捕获和宏展开。
  - `core/deduction.ts`：规则、命题、推理步骤的数据结构。
  - `core/assert.ts`：断言和原子约束求解。
  - `core/combine.ts`：组合规则、MCPT、MSBT 及元规则步骤生成。
  - `main.ts`：推理层 UI、命令注册和规则/推理表交互。
  - `gui/sheet.ts`：多张推理表的切换、增删、改名和排序。
  - `serde.ts`：推理层存档序列化。
- `src/tt/`：类型层。
  - `parser.ts`：类型表达式解析与输入替换。
  - `kast.ts`：界面 AST 与内核 AST 的转换。
  - `nbe-kernel.ts`、`nbe-checker.ts`：归一化和类型检查内核。
  - `core.ts`：类型层门面，提供定义、断言、类型推断、归一化和执行。
  - `initial.ts`：初始系统定义；创造模式加载完整 HoTT 系统。
  - `gui.ts`、`main.ts`：系统表和定理表 UI。
- `src/pg/`：进度层 UI，以及存档槽位、成就、知识库显示。
- `src/saveload.ts`：当前模式存档、导入导出、槽位和 LZ-String 压缩。
- `src/astrender.ts`、`src/asttype.ts`：语法高亮、编辑器和 AST 公共设施。
- `style/`：各层样式。
- `test/`、`tools/`：Node 测试和开发验证脚本。

## 三、创造模式的初始化状态

进入 `index.html?creative` 后：

1. 推理层加载 `initialCreativeRules`，包含逻辑公理、逻辑定义、系统定理以及大量可展开的元规则。
2. 类型层创建完整 HoTT 系统，而不是生存模式使用的最小类型系统。
3. `c`、`v`、`f` 等基础元操作以及基础命题/规则命令被开放。
4. 知识库在创造模式直接视为全部解锁，因而不需要走地图奖励流程。
5. 第一次进入时默认切到进度层；之后加载存档中记录的当前层。

创造模式存档只包含：

- 推理层的规则和所有推理表；
- 类型层定理表；
- 当前所在层。

生存模式专用的几何世界、奖励、成就、推理素、拆门状态和知识库解锁集合不会写入创造模式存档。存档使用模式键隔离，模式不匹配时会跳转到对应模式。

## 四、推理层：Hilbert 证明沙盒

### 4.1 三个基本对象

推理层有规则表、推理表和命令栏。

#### 规则

规则由三部分组成：

```text
规则名: 断言; 假设 ⊢ 结论;
```

- 断言限制替换元变量或普通变量的取值。
- 假设是使用规则时必须提供的前提。
- 结论是规则推出的结果。
- 规则还可以带一棵中间推导步骤树；这使它既能直接使用，也能按需展开查看。

规则名约定：

- `a...`：公理，例如 `a1`、`a2`。
- `d...`：定义或系统规则。
- `....`：系统定理，例如 `.i`、`.t`。
- 用户自定义规则不能以 `a`、`c`、`d`、`e`、`m`、`p`、`u`、`v`、数字、`#`、`$`、`%`、`<`、`>` 或 `.` 开头，以免和命令、系统规则、元规则冲突。

创造模式的起点包括：

```text
mp:ax: $1→$2, $1 ⊢ $2;
a1:ax: ⊢ $1→$2→$1;
a2:ax: ⊢ ($1→$2→$3)→($1→$2)→($1→$3);
```

其中 `$1`、`$2` 等是 wff 替换元变量；规则应用时系统会寻找满足条件的具体表达式。

#### 推理表

推理表是一棵有序的证明步骤列表。一个项目可能是：

- `hyp`：用户输入的假设；
- `a`：断言步骤；
- `d`：调用规则得到的新命题；
- `c`：条件文件夹；
- `v`：变量/全称量词文件夹；
- `f`：普通文件夹，用来整理步骤。

一张推理表就是一个独立证明上下文，但所有推理表共享同一套规则。可以新建多张表，用于分别尝试证明、保存中间结果或加载宏规则。推理表支持改名、删除、拖拽排序和文件夹折叠。

#### 命令栏

命令栏支持用分号或换行连续输入命令。命令参数不足时，系统会进入交互补全：提示下一个参数，用户可以直接输入，也可以点选推理表中的命题。`ESC` 会回退一个参数或取消当前命令，`OK` 提交命令。

常用命令形态包括：

```text
hyp 公式                 添加假设
cond 公式                新建条件文件夹
var 变量                 新建全称量词/变量文件夹
d 规则名 参数...         使用规则
cd 编号                  关闭/退出当前条件层级
```

具体命令以命令栏的提示和 `src/hs/main.ts` 中的注册为准。规则参数可以省略，交给交互式参数请求补全；已经在表中的命题也可以通过编号引用。

### 4.2 推理、宏和肢解

使用规则时，系统会：

1. 解析规则名和参数；
2. 将规则的替换元变量匹配到实际命题；
3. 检查断言和条件是否满足；
4. 创建新的命题，并把它放入当前推理作用域；
5. 若规则有中间步骤，则记录可供展开的证明树。

带中间步骤的规则可以在菜单中选择“肢解”。肢解不是简单复制显示文本，而是重新播放命令并重建命题之间的依赖，因此展开后仍能正确引用原来的结论和作用域。展开失败会回滚，不留下半成品。

规则本身也可以通过菜单“加载宏”重放到推理表中；系统会重新执行其命令，而不是共享规则内部的命题对象。这样后续肢解不会污染规则定义。

### 4.3 内联元规则

内联元规则是写在推理表中的特殊步骤，系统根据已有证明按需生成更高层的证明。主要形式如下：

- `c`：条件化。若在假设 `$A` 下推出 `$B`，就生成 `$A→$B`。
- `v`：概括。若在变量 `$x` 的适当作用域内推出 `$A`，就生成 `∀$x:$A`。
- `e`：存在化。引入新的局部常量，把一个实例提升为存在命题。
- `<`：逆演绎元定理，把蕴含结论拆成可使用的规则结构。
- `>`：演绎元定理，把最后一个条件提升为蕴含结论，即从 `A,...,B ⊢ C` 生成 `A,... ⊢ B→C`。
- `mcpt`：命题完备性/自动命题推理，验证一个纯命题逻辑模板后生成步骤。
- `msbt`：按匹配模板替换公式或推理步骤，可指定全部、正向或反向的匹配位置。
- 组合规则：用一个规则的条件匹配其它规则的结论，自动合成新规则。

`c`、`v` 的展开会显式生成 `hyp`、`cond`、`var`、`d` 和 `mp` 等普通步骤；因此菜单肢解后可以检查它究竟依赖了哪些证明。

### 4.4 `#sb` 替换函数

`#sb` 是推理层中处理变量替换的核心函数，形式可理解为：

```text
#sb(主体, 源变量, 目标表达式, 约束变量集合)
```

它负责在量词、函数、谓词和集合构造中安全地替换变量，并避免变量捕获。化简大致遵循以下顺序：

1. 源变量是当前自由变量且目标表达式满足自由变量约束时，直接替换。
2. 主体是常量、目标与源相同，或源变量不在主体中自由出现时，删除替换层。
3. 对逻辑连接词、谓词和函数应用递归分配替换。
4. 遇到量词或类构造时，把绑定变量加入约束集合再递归。
5. 删除已经不影响替换的冗余约束。
6. 对嵌套替换进行安全交换和化简。
7. 无法证明安全时保留原式或报错，而不是猜测结果。

因此，`#sb` 不是普通的字符串替换。它依赖当前可证明的前提，目标是实现捕获避免的、可验证的替换。

### 4.5 断言系统

规则前可以添加断言。主要断言是：

- `nf a B C`：`B` 中的变量不在 `a` 中自由出现；`C` 提供额外的绑定/约束变量集合。
- `of a B`：`a` 的自由变量只能来自集合 `B`。
- `dt A`：变量集合 `A` 中的变量两两不同。

系统会把可分配的复杂断言拆成原子约束，再由 `AtomSolver` 求解。量词会改变自由变量和绑定变量的范围；涉及无法化简的 `#sb` 时，断言可能保持未知并导致规则不能使用。

断言的意义是让元规则知道哪些替换是安全的，而不是把所有形式看起来相似的表达式都强行接受。

## 五、类型层：HoTT 定义与类型检查

类型层是和 Hilbert 推理层并列的另一套形式系统。它不是把类型表达式当作普通 wff，而是使用独立的解析器、内核 AST、检查器和归一化算法。

### 5.1 系统表和定理表

类型层有两张表：

- 系统表是只读的完整基础库，按类型或定义分组显示。
- 定理表由用户编辑，用户输入一条表达式后，系统立即检查其类型。

定理表的普通命题没有可编辑名字，名称列显示整棵树的前序行号；文件夹可以命名、删除、设为活动文件夹。点击命题内容可以就地编辑，编辑器和显示器使用同一套 TypeParser 高亮。

检查成功时显示 `✓` 和推断类型；失败时显示 `⚠` 及错误信息。检查结果是运行时缓存，不作为定理内容写入存档。

### 5.2 创造模式的初始 HoTT 系统

创造模式通过 `initCreativeRules()` 加载完整系统，当前基础内容包括：

- `True`、`False`、`Bool`、`nat`；
- 相等类型 `eq`、路径构造子 `refl`、相等归纳；
- 依赖积 `Σ`、无交并 `Sum`、`List`、`Option`；
- 整数 `Z`、偶数 `Even`、自然数的归纳与递归定义；
- 圆、悬挂、宇宙提升、命题/可缩性/集合等 HoTT 结构；
- 计算规则、消去子、函数外延性或其它系统公设对应的定义/定理。

类型层支持显式宇宙参数和 scheme 多态：定义中尚未确定的宇宙层级或类型元变量，会在每次使用时实例化并根据上下文求解。系统也支持若干面糖，例如 `x=y`、`A+B`、`A×B`、`(a,b)`、`refl x` 和自然数字字面量。

### 5.3 类型层的玩法

一个典型流程是：

1. 在定理表中新增命题或文件夹。
2. 输入一个类型、构造子应用、函数定义或证明项。
3. 等待 Core 解析并推断类型。
4. 观察成功的类型结果，或根据错误信息修改表达式。
5. 使用已有定义和归约规则构造更复杂的项。

例如可以从 `True`、`nat` 和 `succ` 开始，逐步定义自然数函数；也可以使用 `eq`/`refl` 构造相等证明，再用 `ind_eq`、`trans`、`inveq` 等系统项组合路径。

类型层更像一个小型交互式证明助手：输入的是证明项/定义，输出的是类型检查结果，而不是推理层那种“从假设列表逐步推出结论”的命题表。

## 六、创造模式的推荐上手路线

### 路线 A：先熟悉推理层

1. 打开 `?creative`，进入推理层。
2. 用 `hyp` 添加两个简单命题，例如 `$p` 和 `$p→$q`。
3. 用 `d mp` 选择这两个命题，得到 `$q`。
4. 新建 `cond`，在条件中重复上面的推理，理解作用域如何包住步骤。
5. 尝试用 `c` 将条件证明提升为蕴含。
6. 在规则表中查看生成的规则，并对带步骤的规则执行“肢解”。

### 路线 B：建立自己的逻辑库

1. 从 `a1`、`a2`、`mp` 和已有系统定理开始。
2. 证明常用引理并整理到规则文件夹。
3. 给规则重命名，让规则名反映用途。
4. 使用组合规则或 `mcpt` 缩短重复证明。
5. 用 `msbt` 做等价替换和结构化重写。

### 路线 C：从类型层开始 HoTT

1. 先浏览系统表，认识每个类型的 `TYPE`、`CTOR`、`IND`、`DEF` 和 `COMPUTE` 项。
2. 在定理表添加 `true`、自然数和简单函数应用。
3. 练习 `refl`、函数应用和归纳子。
4. 使用 `eq`、`trans`、`inveq` 组合相等路径。
5. 再进入 `Σ`、`Sum`、`List`、`Z` 和高阶同伦相关结构。

## 七、存档、UI 和数据边界

### 存档

`SaveLoad` 把当前状态序列化为带有版本、模式、时间戳和数据的包，再用 LZ-String 压缩到 `localStorage`。创造模式的主存档键是 `deductrium2_creative`；进度层还提供四个独立槽位，可保存、加载、导出和删除。

状态改变后不会每次操作立即写盘，而是通过约 2 秒的延迟保存合并连续变化。导入文件会检查格式和模式；模式不匹配时跳到该存档所属的模式。

### UI 约定

- `TreeListViewer` 负责规则表、推理表和类型层表格的树形显示、折叠、菜单和拖拽。
- `SyntaxViewer` 负责只读语法高亮。
- `SyntaxEditor` 负责命令栏和类型层就地编辑。
- 多语言静态文本统一由 `LangMgr.applyStaticI18n()` 处理。
- 推理层和类型层的变更通过 `onchange` 回调通知 `Game`，再交给 `SaveLoad.notifySave()`。

## 八、开发和验证约定

源码修改应集中在 `src/`，由 TypeScript 编译到 `js/`。修改推理层时重点检查 AST、规则重放和作用域；修改类型层时重点检查 parser、KAST 转换、NBE 内核和类型错误显示。

已有的创造模式相关测试包括：

- `test/test-expand.mjs`：规则/文件夹肢解；
- `test/test-combine.mjs`：组合规则；
- `test/test-cvstep.mjs`、`test/test-cvexpand.mjs`：条件化和概括；
- `test/test-gtrule.mjs`、`test/test-ltrule.mjs`：演绎元规则；
- `test/test-errorrule.mjs`：错误规则；
- `test/test-loadclone.mjs`：宏加载后的对象隔离；
- `test/test-tt-core.mjs`：类型层 Core；
- `test/test-tt-initial.mjs`：创造模式完整初始 HoTT 系统。

这些测试通常用 Node 的 ES module 模式运行。浏览器交互问题则应在 `?creative` 页面中分别验证：命令执行、规则肢解、推理表切换、类型检查、自动保存和刷新后恢复。

## 九、当前明确的边界

- 本文只描述创造模式的数学沙盒玩法。
- 几何层 `src/hy/` 和尺规层 `src/rl/` 属于几何/实验模块，不是创造模式当前的主要玩法；创造模式不会显示 G-layer。
- 地图门、奖励、推理素、成就触发、移动和生存解锁属于生存模式流程。
- 类型层当前是显式参数风格，worker 和 `@` 别名等原版功能没有全部移植。
- 推理层的自动化仍以规则匹配和有限的元规则为基础，不是开放式自然语言证明器。
